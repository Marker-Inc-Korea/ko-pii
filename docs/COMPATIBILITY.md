# Compatibility Contract / 호환성 정책

## 지원 표면

1.x에서는 `ko_pii.__all__`에 공개한 이름과 문서화된 코어 메서드를 유지하는 것을
원칙으로 합니다. 선택 의존성의 upstream 변경은 별도 영향을 줄 수 있습니다.
밑줄로 시작하는 함수·모듈 내부 구현·연구 스크립트는 안정 API가 아닙니다.
문서에 사용법이 있다는 이유로 모든 하위 모듈 심볼이 공개 계약이 되지는 않습니다.

기존 호출에 필수 인자를 추가하거나 위치 인자 순서를 바꾸는 변경은 호환성 변경으로
취급합니다. 보안상 잘못된 입력을 거부하는 강화는 patch/minor에 들어갈 수 있으며
CHANGELOG에 마이그레이션 안내를 적습니다. 선택 인자 추가는 기존 기본 동작을 유지합니다.
제거가 필요하면 먼저 문서와 경고로 폐기를 알리고 다음 major에서 제거하는 것이 원칙입니다.

탐지 규칙·사전의 개선으로 탐지 결과와 토큰 부여 순서는 달라질 수 있습니다.
기존 토큰 문자열을 전체 버전에 걸친 영구 식별자로 취급하지 마세요.
같은 Vault 상태에서 같은 (라벨, 원문) 쌍을 재사용하는 계약과는 별개입니다.
업그레이드 전 자체 라벨셋·정책으로 출력 회귀를 확인하세요.

1.22.12부터 공개 직접 변환 함수는 원문과 탐지 좌표·텍스트가 일치하는지 먼저 검사합니다.
빈/범위 밖 좌표와 다른 원문에서 얻은 탐지 결과를 조용히 적용하지 않습니다.
`hashed`의 `digest_len`도 1~64 정수로 제한합니다. 정상 입력과 안전한 사용자 정의 라벨은
유지하며, 자세한 오류/반복자 경계는 [직접 변환 API](TRANSFORMATION_API.md)를 참고하세요.

1.22.13부터 XLSX Strict 시트의 셀을 실제로 읽으므로 이전에 누락되거나 빈 추출 오류가
나던 입력의 결과가 달라집니다. 알 수 없는 XLSX 루트/네임스페이스는 빈 시트로 통과시키지
않습니다. 기존 Transitional 셀 처리와 파일 제한은 유지합니다. 범위는
[파일 처리](FILE_PROCESSING.md)를 참고하세요.

1.22.14부터 HWPX의 텍스트 요소 안에서 탭·줄바꿈·표시 태그 뒤에 이어지는 문자열을
누락하지 않습니다. 이전에 읽히지 않았던 내용 때문에 추출 길이, 탐지 좌표와 토큰 순서가
바뀔 수 있습니다. 단순 문단의 출력과 파일 제한은 유지하며 탐지 규칙 자체의 변경은 아닙니다.

1.22.15부터 content.hpf가 있는 HWPX는 선언된 본문 순서와 지원 메타데이터를 반영합니다.
목록/본문 참조가 깨진 파일은 발견된 일부 섹션만 읽어 성공하지 않습니다. 목록이 없는
기존 입력은 숫자순 섹션 탐색을 유지합니다. 내용·순서가 복원되므로 추출 좌표와 새 토큰
순서는 바뀔 수 있습니다. 기존 Vault를 다시 번호 매기거나 원본 문서를 수정하지 않습니다.

1.22.16부터 XLSX는 통합문서의 시트 순서와 시트/공유 문자열 참조를 사용합니다.
목록이 깨지거나 참조된 시트가 없는 파일은 일부만 읽어 성공하지 않습니다. 기존 최소
테스트 파일도 workbook.xml을 넣었다면 올바른 시트 목록과 관계 파일을 함께 제공해야
합니다. 목록이 모두 없는 저수준 입력만 숫자순 탐색을 유지합니다. 출력 순서·좌표·새 토큰은
바뀔 수 있지만 기존 Vault를 변경하지 않습니다. 전체 패키지 검증이 아니라 지원 참조 검사입니다.

## CLI

`ko-pii`의 문서화된 옵션은 위 호환 원칙을 적용합니다.
일반 처리는 성공 0, 처리 실패 1, 인자·설정 오류 2를 구분합니다.
평가 CLI는 회귀 임계값 실패에 별도 비정상 종료를 사용할 수 있으므로 해당
`--help`와 평가 문서를 따르세요. stderr의 사람용 문장을 파싱하는 것은 지원하지 않습니다.

## JSON과 좌표

보고서는 각 문서의 `schema_version` 또는 `contract`를 확인해 소비합니다.
패키지 버전과 보고서 계약 버전은 별개입니다. 기존 필드의 의미를 바꾸거나 필수 필드를
제거할 때는 해당 계약을 변경합니다. 소비자는 추가 출력 키를 허용해야 합니다.
반대로 설정 입력(PolicyProfile 등)은 오타 방지를 위해 알 수 없는 키를 거부할 수 있습니다.
기존 포맷에 버전 필드가 없다면 소비 전에 버전별 가이드를 확인하고 임의 추정을 하지 마세요.

탐지 span은 Python 문자열의 문자 인덱스, 반개구간 [start, end)입니다.
바이트 위치나 JavaScript UTF-16 인덱스가 아닙니다. 정규화 탐지는 원문 좌표로 복원합니다.
값 없는 보고서도 위치·라벨·길이 정보를 포함하므로 공개 전에 민감성을 판단하세요.

1.22.10부터 분해형 한글의 원문 위치는 단어 전체가 아닌 합성 음절 단위로 추적합니다.
예를 들어 NFD로 저장한 `홍길동에게`에서는 이름 전체를 치환하고 `에게`는 원래 형태로
남깁니다. 한 호환문자가 여러 문자로 펼쳐질 때 탐지 구간이 그 일부에만 걸쳐도 원래
문자 전체를 포함합니다. 원문 문자를 나눠 치환할 수 없어 보수적으로 범위를 넓히는 것입니다.
따라서 `source[start:end] == detection.text`뿐 아니라 예상한 전체 원문 범위를 실제로
치환했는지도 검증해야 합니다. 빈 구간도 앞의 등식만은 만족할 수 있습니다.

한글 L+V(+T), LV+T 조합 경계는 [Unicode 3.12의 한글 합성 규칙](https://www.unicode.org/versions/Unicode17.0.0/core-spec/chapter-3/)
에 따릅니다. ko-pii의 탐지용 정규화에는 별도로 보이지 않는 문자 제거와 숫자 닮은꼴
처리가 있으므로 일반적인 Unicode 정규화 함수의 대체품은 아닙니다. 탐지용 문자열을
바꾸더라도 치환 대상 밖의 원문은 재정규화하지 않습니다. `normalize=False` 또는
AUDIT로 호출하면 각각 정규화 생략 또는 원문 보존이라는 기존 정책이 적용됩니다.

## Vault와 정책 파일

1.22.11부터 FRN의 레거시 검증 숫자를 RRN과 구분합니다. 따라서 FRN 신뢰도와 정책에
따른 치환 여부, FRN FPE의 마지막 숫자가 달라질 수 있습니다. 검증 숫자 실패 근거도
`checksum:invalid_or_post_2020`에서 `checksum:unverified`로 바뀝니다.
과거 발급 시점을 판정하는 값으로 사용하지 마세요. 자세한 범위와 출력 전환 주의사항은
[식별번호 검증](IDENTIFIER_VALIDATION.md)을 참고하세요. 기존 Vault를 자동 변경하지 않습니다.

Vault JSON schema 1과 PolicyProfile schema 1의 유효한 기존 파일을 읽을 수 있도록 검사합니다.
미지원 schema, 중복/충돌 매핑과 손상된 값은 거부하며 자동 보정·묵시적 재번호를 하지 않습니다.
암호화 파일과 키 관리 범위는 [Vault 보안](VAULT_SECURITY.md)을 참고하세요.
JSON Vault는 평문 개인정보를 담습니다. fixture의 값은 합성이며 운영 Vault를 커밋하면 안 됩니다.

1.22.0 PyPI wheel로 만든 고정 fixture는 export·생성자 호출 형태·Vault 복원과 다음 토큰·
정책 fingerprint·EMAIL 설명 좌표·CLI 출력을 검사합니다.
이것은 유용한 회귀 감지 장치이지 모든 과거 버전/모든 API 조합의 호환성 증명은 아닙니다.
서로 다른 버전의 동일 탐지율 또는 모든 선택 모델의 재현성도 보장하지 않습니다.

## 보안 지원

수정은 최신 1.x 릴리스에 제공하며, 모든 과거 minor에 병렬 backport를 약속하지 않습니다.
취약점 대응과 보고 채널은 [SECURITY](../SECURITY.md)가 기준입니다.
