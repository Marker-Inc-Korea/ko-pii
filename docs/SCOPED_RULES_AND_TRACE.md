# 필드별 제외, 사용자 정의 규칙, 설명 추적

1.21.0에서 추가된 기능입니다. `python -m pip install --upgrade 'ko-pii>=1.21.0'`으로 설치합니다.
소스에서 사용하려면 소스 디렉터리에서 `python -m pip install -e .`를 실행합니다.
서버, OCR, 분류기 또는 새 런타임 의존성을 추가하지 않습니다.

## 명시적 이름 필드의 경계 (1.22.18~1.25.0)

`성명: 김다은`, `성명: 김빛나라`처럼 경계가 분명한 2~4음절 이름 값은 마지막 음절을
조사로 추측해 자르지 않습니다. `성함`, 이름/신청인 등 기존 이름 필드, 띄어 쓴 라벨,
콜론/등호/탭/줄바꿈 구분도 인식합니다. `성명`과 `성함`은 사람 전용 신호로 보고,
범용 `이름`에는 기존 일반어·기관명 제외를 적용합니다. `파일이름` 같은 부분 라벨이나
`성명: 없음`은 이름 근거가 아닙니다. 필드에서 확인한 이름은 같은 문서의 앞뒤 등장에도
재사용하지만 다른 `process()` 호출로 전파하지 않습니다.

```python
from ko_pii import Anonymizer

anon = Anonymizer(include=["PERSON"], strategy="redact")
assert anon.process("성명: 김다은\n성명: 김빛나라").text == "성명: [성명]\n성명: [성명]"
assert anon.process("성명: 홍길동이 신청서를 냈다.").text == "성명: [성명]이 신청서를 냈다."
```

단독 필드의 `홍길동은`처럼 마지막 음절의 의미가 모호하면 전체 값을 보호하는 쪽을
택합니다. 조사가 함께 가려질 수 있고, strict span 평가에서는 정답보다 긴 탐지로
계산됩니다. 서술문과 달리 필드값 자체만으로 실제 이름의 경계를 증명할 수 없기 때문입니다.
`tokenize`의 Vault 원문에도 해당 값 전체가 들어갑니다. 외부 공급자에게 출력하거나
기존 버전과 결합하기 전에 실제 마스킹 결과와 복원 범위를 확인하세요.

이는 텍스트 휴리스틱이며 이름 인증이나 모든 도메인의 완전한 탐지가 아닙니다.
필드 의미가 스키마로 확정돼 있다면 기존 `field_labels`/표의 `column_map` 단언을
사용할 수 있습니다. `person_exclusions`의 정확한 전체값 제외는 이 휴리스틱보다 우선하고,
명시적 `field_labels` 단언의 우선순위와 AUDIT 원문 보존은 바꾸지 않습니다.

1.23.0에서는 CR/VT/FF/NEL/Unicode 줄·문단 구분, 빈 줄과 `“김다은”`, `「김다은」` 같은
인용부호도 인식합니다. 필드 주변 구분자와 인용부호는 출력에 보존합니다. 라벨 근거는
이름 직전 최대 32자의 문법으로 한정하며 멀리 떨어진 표 제목을 추측 연결하지 않습니다.
`담당자`, `작성자`도 이름 필드에 포함합니다. `담당자는 김다은입니다`처럼 사람 역할과
서술격 어미가 명확하면 이름을 확인하고 같은 문서에서 재사용합니다. 역할이나 필드 근거
없이 `김다은이며`라는 단어만으로 모든 인명을 새로 찾는 범용 NER는 아닙니다.

1.24.0에서는 `[성명] 김다은`, `【성명】 김다은`, `**성명**: **김다은**`,
`__성명__: __김다은__`, 백틱 라벨/값과 `| 성명 | 김다은 |`도 인식합니다.
`참석자: 김다은, 박보라`처럼 같은 줄·셀의 한글 항목이 쉼표, `/`, `&`, 가운데점,
하이픈으로 이어지면 각 지원 이름을 처리합니다. 빈 값이나 명시적 제외어 항목이 있어도
다음 지원 이름을 무조건 놓치지 않습니다. 목록의 다음 이름에는 기존 근거와 함께
`pattern:person_name_field_list`가 추가됩니다. 구분자와 강조/인용 문자는 가리지 않습니다.

```python
assert anon.process("[성명] 김다은·박보라").text == "[성명] [성명]·[성명]"
assert anon.process("**성명**: **김다은**, **박보라**").text == "**성명**: **[성명]**, **[성명]**"
```

이것은 한글 이름 필드 문법 보완이지 Markdown/CSV 전체 파서가 아닙니다. 다른 줄의
표 제목, 다음 `|` 셀, 서술문으로 목록 문맥을 넘기지 않습니다. 1.24.x까지는 한 글자·긴
이름, 로마자·혼합 문자 목록 등에 스키마 단언이나 업무별 규칙이 필요했습니다.
이름 필드와 `3호선` 같은 공공 정보도 포함한 업무별 오탐·미탐 검사는 계속 필요합니다.

1.24.1부터 명시적 목록의 `N/A`, `N.A.`, `NA`, `NULL`, `None`은 대소문자와 기존
인용/강조 표기를 허용하는 빈 항목입니다. 표시는 보존하고 같은 목록의 다음 지원 이름을
계속 처리합니다. `nullable`, URL의 `/NA`, 다음 줄·셀 등에는 이 문맥을 부여하지 않습니다.
모든 영문 값이 빈 항목이거나 모든 로마자 이름을 탐지한다는 뜻은 아닙니다.

### 긴 이름·영문·한자 표기 (1.25.0)

`성명`과 `성함`에는 다음과 같은 이름 형태의 명시적 값을 지원합니다. 범용 `이름`,
`신청인`, 임의 본문에 같은 확장 문법을 부여하지 않습니다.

```python
assert anon.process("성명: 장피에르뒤퐁").text == "성명: [성명]"
assert anon.process("성명: 김 민수").text == "성명: [성명]"
assert anon.process("성명(영문): Anne-Marie O'Neill").text == "성명(영문): [성명]"
assert anon.process("성명: 김민수 (金民秀)").text == "성명: [성명] ([성명])"
assert anon.process("성명: __John Smith__\nJohn Smith").text == "성명: __[성명]__\n[성명]"
```

Unicode 문자/결합 표시, 이름 안의 공백, 로마자 사이 하이픈·아포스트로피와 이니셜 점을
인식합니다. 따옴표·강조 안의 앞뒤 공백은 남깁니다. 따옴표가 없는 한글 다중 단어는
알려진 성씨와 이름의 두 부분으로 한정해 임의 문장을 이름으로 삼키지 않도록 합니다.
`성명(영문)`/`성명(영어)`/`성명(한자)`도 지원합니다. 괄호 안의 값도 지원 이름 형태와
일반어 제외 조건을 통과해야 하며 모든 주석을 개인정보로 간주하지 않습니다.

같은 줄·셀의 쉼표·슬래시·`&`·가운데점·하이픈 목록은 한글·영문·한자를 섞어 처리할 수
있습니다. 다음 줄·탭·`|` 셀·세미콜론으로 확장 목록 문맥을 넘기지 않습니다. 한 항목은
정규화 뷰에서 이름의 시작부터 최대 128자이며 초과 값의 앞부분을 완전한 이름으로 주장하지 않습니다.
숫자·밑줄이 들어간 식별명과 미지원 값은 자동 보호된다고 가정하지 말고, 스키마를 아는
경우 `field_labels`/`column_map` 또는 `LiteralDetector`를 사용하세요.

확인된 정확한 값은 같은 문서의 앞뒤에서 단어 경계와 한정된 조사/서술격 어미를 확인해
재사용합니다. `John Smith`의 `XJohn Smith`/`John SmithX` 속 조각은 재사용하지 않으며
줄을 이어 붙이거나 이름의 일부만으로 같은 사람을 추론하지 않습니다. 한 글자 값도
강한 필드에서는 지원하므로 `성명: A`가 있다면 본문의 독립 `A`도 처리될 수 있습니다.
업무별 과다 마스킹을 확인하세요. 비교는 기본 정규화 뷰의 대소문자 구분 문자열 기준이고,
원문 치환·Vault에는 실제 원문을 사용합니다. 다른 호출에는 이름 문맥을 전파하지 않습니다.

확인된 확장 필드 값이 정확한 전체값 제외어라면 그 필드와 지원 단어 경계로 확인한
같은 문서의 반복 구간을 기존의 부분 이름 후보가 다시 가리지 않습니다. `남궁 다은`을
제외했다고 별도 필드나 다른 위치의 `남궁`/`다은`을 전역 허용하는 것은 아닙니다.
겹치는 다른 유효 개인정보 후보까지 허용하거나 다른 라벨의 보호를 끄는 규칙도 아닙니다.

탐지 객체 `evidence`의 확장 값 근거는 `pattern:person_literal_name_field`입니다. 값 없는
설명 보고서는 기존의 허용 목록만 내보내고 임의 evidence는 포함하지 않습니다.
점수는 기존 강한 필드와 같은 규칙 등급이지 정확도 확률이 아닙니다. 이름이 새로 처리되거나 겹친 후보의 나머지가 별도
구간으로 보호되면 탐지 건수·신규 토큰 순서·Vault 단위가 달라질 수 있습니다.

`extra.origin`의 `korean`/`foreign`/`unknown`은 레거시 문자열 형태 태그입니다. 국적,
실제 출신이나 보호 대상 여부를 판정하지 않으며 기본 마스킹에서 이름을 제외하지 않습니다.
긴 한글 이름도 `foreign`, 한자·로마자도 `unknown`을 받을 수 있습니다. 이 태그나
KLUE의 별도 형태 제한 표본 점수를 실제 업무의 제외 기준으로 쓰지 마세요.

긴 한글 값의 마지막 한 음절이 조사와 같아도 실제 이름의 일부일 수 있으므로, 명시적
필드의 `성명: 김마리아은`에서는 전체 값을 보호합니다. 실제로 조사가 붙은 값이면 그
조사까지 가려지고 Vault에도 포함될 수 있으며 strict span 점수는 낮아질 수 있습니다.
알려진 서술격 어미와 짧은 이름 뒤의 다중 음절 조사는 별도로 확인합니다. 필드 값만으로
항상 정확한 이름 경계를 판정할 수 없으므로 복원·다운스트림 소비 범위도 검증하세요.

### 뒤따르는 양식 항목 (1.26.0)

`성명: 김빛나라 전화번호: ...`나 `성명: John Smith **이메일**: ...`에서는 알려진
다음 항목 앞에서 이름을 끝냅니다. 뒤 항목 때문에 이름 전체를 놓치거나 마지막 음절을
남기지 않고, `생년월일(양력)` 같은 항목명·설명을 이름에 흡수하지 않습니다.

```python
assert anon.process("성명: 김빛나라 전화번호: public").text == "성명: [성명] 전화번호: public"
assert anon.process("성명: John Smith **이메일**: public").text == "성명: [성명] **이메일**: public"
assert anon.process("성명: 金民秀 생년월일(양력): public").text == "성명: [성명] 생년월일(양력): public"
```

경계는 표 헤더의 알려진 별칭, 기존 항목명과 한정된 양식 메타데이터에 한합니다.
`고객 연락처`, `customer_email` 같은 알려진 주체 접두사도 지원합니다. 프레임의 짝과
콜론/등호가 필요합니다. 기본 별칭 자체의 `(한글)`/`(양력)`/`(음력)` 표기 외에 추가하는
괄호 설명은 같은 줄의 탭을 넘지 않는 32자 이내이며 프레임 안이나 밖 한 곳에 둘 수
있습니다. 알 수 없는 `UnknownField:`, 부분 단어
`전화번호부:`, 깨진 프레임을 정상 항목으로 추측하지 않습니다.

이 인식은 앞 이름의 경계만 정합니다. 다음 항목에 PERSON 근거를 새로 주거나 값을
자동으로 특정 라벨로 단언하는 것이 아닙니다. 그 값의 일반 탐지는 기존 탐지기가,
표 전체 값 단언은 검증한 스키마 매핑이 담당합니다. 임의 문서 레이아웃 전체를 해석하는
파서가 아니므로 미지원 구문이 자동 보호된다고 가정하면 안 됩니다.

## 상세주소 단위 (1.24.0)

확인한 도로명/지번 주소 뒤 `B1층`, `b2층`, `B101호`, `지하1층`, `지상 2층`,
`A동101호`, `가동101호`, `101호실`, `101동/1202호`, `101동-1202호`를 포함합니다.
`101호에서`처럼 구분되는 조사는 남기며 `3호선`, `101동작`의 일부를 상세로
삼키지 않습니다. 상세주소가 아닌 임의 명사나 모든 실제 건물명을 추론하는 기능은 아닙니다.

1.24.1에서는 `101동근처에서`, `1202호앞에서`, `12층로비에서`, `101동입니다`와
붙여 쓴 `101동에서만나요`도 단위 뒤 문맥으로 인식합니다. 1.24.0에서 동호수가 남던
회귀를 복구한 것입니다. 알려진 위치 명사·조사·서술형을 확인하되 치환/Vault에는 단위까지만
포함하므로 `근처에서`, `앞에서`, `로비에서` 등은 원래대로 남습니다. Markdown의
밑줄도 주소 바깥에 남깁니다. `101동내역`, `12층로비스트` 같은 다른 단어로 확대하지 않습니다.

숫자와 붙은 `호실`, 층수 앞의 `지하`/`지상`, 숫자 호수 앞의 한 글자 동 표기를
전화번호가 가깝다는 이유만으로 일반 이름 후보로 올리지 않습니다. 다만 명시적 이름
필드나 같은 문서에서 이미 확인한 이름은 우선하므로, 중의적 단어는 업무별 확인이 필요합니다.

## 겹치는 완전 치환 후보의 나머지 보호 (1.23.0)

주소 안의 전화번호는 고위험 전화번호를 우선 선택하면서도 주소의 나머지를 보호해야 합니다.

```python
from ko_pii import Anonymizer

source = "주소: 서울특별시 강남구 테헤란로 152 (010-1234-5678)"
result = Anonymizer(strategy="redact").process(source)
assert result.text == "주소: [주소][전화번호][주소]"
assert result.summary["overlap_protection"] == {"fragments": 2}
```

병합·필터·정책을 적용한 뒤, 버려진 BLOCK 후보의 전략이 `redact`, `tokenize`, `asterisk`,
`hashed`라면 선택된 BLOCK 구간 밖의 나머지를 분리해 처리합니다. 선택된 고위험 후보의
라벨과 전략은 바꾸지 않습니다. `partial`/FPE 부모 후보와 REVIEW/ALLOW를 복구하지 않고,
`intersection`/`role_split`/`enrich_primary` 등 병합 정책에서 제외된 후보도 사용하지 않습니다.
선택된 전화번호에 `partial`을 지정했다면 그 번호의 의도된 보존 부분은 그대로 남습니다.

분리 구간은 `subrule_id="protection.overlap-remainder.v1"`,
`evidence`의 `protection:overlap_remainder`, `extra.overlap_parent`의 라벨과 부모 원문 좌표로
확인할 수 있습니다. 각 구간의 `text == source[start:end]`이며 겹치지 않습니다. 새로 탐지한
독립 주소가 아니라 원래 후보에서 유래한 보호 구간이므로 탐지 건수를 인원·개체 수로
해석하면 안 됩니다. 임의 `extra`는 값 없는 설명 보고서에 내보내지 않습니다.

토큰 치환에서는 `<ADDRESS_1>`, `<PHONE_1>`, `<ADDRESS_2>`처럼 나뉠 수 있고, 각 Vault
토큰은 해당 원문 조각을 복원합니다. 단일 주소 토큰 하나에 전체 주소가 저장된다고
가정하던 애플리케이션은 전환 전에 확인하세요. 기존 Vault를 재작성하지 않습니다.
비충돌 입력과 탐지 전용 `detect_all()`/공개 `merge_detections()`의 우선순위 선택은 유지합니다.

이 처리는 이미 생성된 후보의 치환 누락을 막는 것이지 탐지하지 못한 값의 존재를
증명하거나 해결하지는 않습니다. 잘못 넓게 잡힌 후보는 주변 문구까지 가릴 수 있으므로
최종 출력의 잔존과 과다 마스킹을 함께 평가하세요.

## 1. 필드에 한정한 PERSON 제외

```python
from ko_pii import Anonymizer, anonymize_json

data = {"product": "홍길동", "customer": "홍길동", "mail": "user@example.com"}
result = anonymize_json(
    data,
    anonymizer=Anonymizer(strategy="redact"),
    field_person_exclusions={"/product": ["홍길동"]},
    field_labels={"/customer": "PERSON"},
)
assert result.data == {"product": "홍길동", "customer": "[성명]", "mail": "[이메일]"}
```

- 정확한 JSON Pointer만 사용합니다. `/items/0/product`는 첫 항목만 선택합니다.
  `*`는 와일드카드가 아닙니다. `/`가 든 키는 `~1`, `~`가 든 키는 `~0`로 표현합니다.
- 제외어는 정규화한 PERSON 후보와 정확히 일치할 때만 적용합니다. 부분 문자열/정규식
  제외는 하지 않습니다. 전화·주민번호·이메일 등 다른 라벨은 제외되지 않습니다.
- 기존 `Anonymizer(person_exclusions=...)`는 여전히 인스턴스 전체에 적용됩니다.
  필드별로만 제한하려면 전역 제외에 넣지 말고 위 설정만 사용하세요.
- `field_labels`와 `FieldRule`은 필드 전체에 대한 명시적 개인정보 단언입니다.
  전역/필드별 제외어로 이를 우회할 수 없습니다. AUDIT 모드의 원문 보존은 유지합니다.
- 원본 객체와 Anonymizer 설정은 바꾸지 않으며 같은 Vault를 계속 사용합니다.
- 최대 128개 경로, 경로당 256개 제외어, 제외어당 256자입니다. 빈 제외어는 거부합니다.
  존재하는 문자열/null 필드만 지정할 수 있습니다. 잘못된 경로/타입은 조용히 무시하지 않습니다.
- JSONL에서도 같은 인수를 사용합니다. 모든 레코드에 해당 경로가 존재해야 하며,
  전체 입력/경로를 선검증한 뒤 처리합니다. 선택 경로와 배열 와일드카드는 이 제외 기능의
  범위가 아닙니다. 외부 탐지기 실패 시 전체 Vault 트랜잭션을 보장하지는 않습니다.
- 제외어는 탐지를 줄이는 정책입니다. 실제 인명과 같은 용어를 제외하면 그 필드에서는
  미탐이 생길 수 있습니다. 별도 라벨링 사례로 영향과 미탐을 함께 확인하세요.

CLI 설정 파일 `field-exclusions.json`:

```json
{"/product": ["홍길동"]}
```

```bash
ko-pii input.json --format json --strategy redact \
  --field-person-exclusions field-exclusions.json \
  --field-label /customer=PERSON -o output.json
```

저장소에 있는 합성 예제로 바로 확인하려면:

```bash
ko-pii docs/examples/scoped-fields.json --format json --strategy redact \
  --field-person-exclusions docs/examples/person-exclusions.json \
  --field-label /customer=PERSON --explain /tmp/ko-pii-scoped-explain.json --trace-limit 20
```

키와 JSON Pointer 자체가 개인정보일 수 있어 설명 보고서는 경로/제외어를 기본 출력하지 않습니다.
설정 파일은 공유 대상에서 제외하세요. 잘못된 경로는 실제 값을 반사하지 않는 오류로 반환합니다.

## 2. 작은 사용자 정의 탐지기

애플리케이션에 이미 있는 패턴을 연결하는 도우미입니다. 자동 규칙 학습, 별도 라벨 체계,
플러그인 설치 서버는 아닙니다. 기존 `secondary_detector` 병합 방식/처리 정책을 그대로 따릅니다.

```python
from ko_pii import Anonymizer, RegexDetector

# 예시: 사내 식별자를 기존 ACCOUNT 처리 정책에 연결합니다.
# 이 매핑은 애플리케이션의 정책 선택이며 새로운 법적 분류를 뜻하지 않습니다.
custom = RegexDetector(r"사번: (?P<id>EMP-\d{4})", label="ACCOUNT", group="id")
anon = Anonymizer(strategy="redact", include=["ACCOUNT"], secondary_detector=custom)
assert anon.process("사번: EMP-1042").text == "사번: [계좌번호]"
```

함수도 연결할 수 있습니다:

```python
from ko_pii import CallableDetector, DetectionResult, RiskLevel

def local_rule(text):
    if text.startswith("ID:") and len(text) > 3:
        yield DetectionResult("ACCOUNT", text[3:], 3, len(text), RiskLevel.HIGH)

anon = Anonymizer(secondary_detector=CallableDetector(local_rule))
```

- 좌표는 정규화 전 입력 문자열의 Python 문자 인덱스입니다. `text[start:end]`와
  탐지값이 일치해야 하며 빈/음수/범위 밖 span, 미지원 라벨, 잘못된 위험도와 NaN/무한대
  신뢰도를 거부합니다. `RiskLevel` enum, 0~1 범위 confidence를 사용하세요.
- 기본 입력 한도 1,000,000자, 결과 한도 10,000개입니다. `max_chars`, `max_matches`로
  설정합니다. 한도/검증 실패를 탐지 0건으로 숨기지 않으며, 전체 출력 검증 후 yield합니다.
- 정규식은 기본 전체 매치를 사용합니다. `group`은 정수/이름 모두 가능하며, 매치하지 않은
  선택 그룹은 건너뛰고 실제로 매치한 빈 그룹은 오류로 처리합니다.
- 원문과 무관한 메타데이터 누출을 피하려고 이 래퍼는 결과의 label/text/span/risk/confidence만
  복사합니다. 자유 형식 evidence/extra/legal_basis/rule_id는 전달하지 않습니다.
  원문을 포함하는 객체 자체와 Vault는 여전히 민감합니다.
- 기존 필터, PERSON 제외, 병합 우선순위와 모드 임계값은 계속 적용됩니다.
  빈 `include=[]`는 기존처럼 설정 오류로 거부됩니다. 전체 라벨은 `include=None`을 사용합니다.
- **신뢰된 개발자가 작성한 코드/정규식 전용입니다.** 실행 시간 제한이나 샌드박스가 아닙니다.
  악성 정규식, 느리거나 멈추지 않는 함수, 외부 API 호출을 차단하지 않습니다.
  입력/결과 개수 제한은 이러한 실행 시간 문제를 해결하지 않습니다.

### 직접 연결한 탐지기의 검증 (1.22)

래퍼 없이 `detect(text)` 메서드가 있는 객체를 연결해도 Anonymizer에서 같은 핵심 검증을
수행합니다. 원문 span/값 불일치, 미지원 라벨, 잘못된 위험도/신뢰도, 잘못된 메타데이터
타입을 해당 문자열의 치환/Vault 저장 전에 거부합니다. 필터로 제외될 라벨이나 AUDIT
모드도 검증을 우회하지 않습니다. 탐지기 예외는 원문을 담지 않는 `ValueError`로 반환합니다.

직접 연결한 결과의 evidence/extra/rule_id 등 정상 메타데이터는 보존합니다.
각 결과와 최상위 evidence/extra 컨테이너를 복사하되 extra 안의 임의 객체까지 격리하는
기능은 아닙니다. 래퍼의 자유 형식 메타데이터 제거 동작은 그대로 유지합니다.
기본 입력/결과 수 제한은 위 래퍼의 기능이지 모든 직접 연결 탐지기의 공통 제한은 아닙니다.

`merge_mode` 오타와 `role_split_labels=["PESRON"]` 같은 미지원 라벨은 생성 시 오류가
발생합니다. `role_split_labels=None`은 기본 위임 라벨, `[]`는 위임 없음으로 유지합니다.
저수준 `merge_detections`도 설정을 검증하지만 원문 인수가 없으므로 span/값의 원문 일치
검사는 Anonymizer 경계에서 수행합니다.

실패한 한 번의 문자열 처리에서 라이브러리의 새 Vault 저장을 막는 것이며 전체 JSON/JSONL
롤백을 뜻하지 않습니다. 탐지기 자체의 부수 효과, 외부 호출, 무한 실행을 막는 샌드박스도
아닙니다. 신뢰한 어댑터만 연결하고 정규화한 결과는 원문 좌표로 역매핑해 반환하세요.

## 3. 값 없는 설명과 제한된 겹침 추적

```python
from ko_pii.reporting import explain

result = Anonymizer(include=["EMAIL"], trace_limit=100).process("user [at] example [dot] com")
report = explain(result, include_trace=True)
assert report["findings"][0]["subrule_id"] == "email.obfuscated.v1"
```

기존 `rule_id`는 탐지기 계열을 유지합니다. 추가 `subrule_id`는 현재 이메일의
`email.ascii.v1`, `email.korean_domain.v1`, `email.obfuscated.v1`과 위의
`protection.overlap-remainder.v1`을 식별합니다.
원문 좌표 역매핑과 보조 탐지기 병합 이후에도 해당 메타데이터를 유지합니다.
정의하지 않은 세부 규칙은 `null`이며 없는 근거를 추측하지 않습니다.

추적은 두 단계의 명시적 선택입니다:

1. `Anonymizer(trace_limit=100)`으로 수집합니다. 기본 0은 수집 안 함, 최대 1,000입니다.
2. `explain(result, include_trace=True)`로 내보냅니다. 기본 보고서는 추적을 넣지 않습니다.

`overlap_trace`에는 공통 겹침 처리의 단계별 후보/채택/탈락 수와, 탈락 후보 및 이를 막은
채택 후보 하나의 라벨/규칙/좌표를 넣습니다. BLOCK 여부, 위험도, 신뢰도, 길이, 시작 위치, 입력 순서 중
어느 우선순위에서 밀렸는지 구분합니다. 해당 단계의 blocker가 이후 병합 단계에서도
최종 채택된다는 뜻은 아닙니다. 원문/토큰/임의 evidence/extra는 포함하지 않습니다.

정책상 비차단 후보가 BLOCK 후보보다 뒤로 선택되면
`non_blocking_policy_priority`를 기록합니다. 1.22.7부터 일반 Anonymizer 탐지 경로의
`overlap_resolution`은 보조 탐지기 유무와 무관하게 `block_risk_confidence_length_start`로
시작합니다. primary 후보를 먼저 버리지 않고 병합 정책과 처리 임계값을 적용한 뒤 선택합니다.
따라서 높은 위험도의 REVIEW 후보가 낮은 위험도의 BLOCK 후보를 숨기지 않습니다.

보조 탐지기가 없으면 `primary`, 있으면 `hybrid` 단계에서 공통 겹침을 기록합니다.
나머지 보호가 발생하면 최종 후보 선택을 `protection` 단계에 추가합니다. 같은 후보가
여러 단계에 집계될 수 있으므로 단계별 후보 수를 고유 개체 수로 합산하지 마세요.
이전처럼 병합 전에 별도의 primary 탈락 이벤트가 생기지 않으므로 추적 집계도 달라질 수
있습니다. 탐지 전용 `detect_all()`은 처리 정책 없이 기존 위험도 우선 방식을 유지합니다.
탐지 전용 결과에 정책을 나중에 적용하는 것을 Anonymizer와 동일하다고 가정하지 마세요.

제한을 넘으면 추가 이벤트를 보관하지 않고 `truncated`, `omitted_events`로 표시합니다.
집계는 계속하며 출력 잘림이 탐지/치환 결과를 바꾸지 않습니다. `overlap_trace: null`은
수집하지 않았다는 뜻입니다. 명시적 필드 단언은 탐지를 거치지 않아 추적이 없습니다.

추적은 모든 탐지 과정의 완전한 설명이 아닙니다. 각 탐지기 내부의 후보 필터,
PERSON 제외, include/exclude, 병합 정책의 후보 제거, 애초에 생성되지 않은 미탐은
기록하지 않습니다. 외부 모델의 판단 이유나 개인정보 부재를 증명하지도 않습니다.
좌표와 라벨만으로도 문서 구조가 드러날 수 있으므로 무조건 공개 가능한 로그는 아닙니다.

```bash
ko-pii input.txt --explain explanation.json --trace-limit 100 -o redacted.txt
```

JSON/JSONL은 문자열 필드마다 독립적으로 한도를 적용하며 전체 보고서의 합계 상한은 아닙니다.
Python에서는 `result.report(include_trace=True)`로 필드별 추적을 출력합니다.
설명 v1의 기존 필드는 유지하고 선택적 `overlap_trace`는 별도 `ko-pii-overlap-trace-v1`
계약으로 관리합니다. 새 필드에 엄격한 소비자는 스키마를 업데이트해야 합니다.

## 4. 개발용 생성형 회귀 테스트

```bash
python -m pip install -e '.[dev,file,security]'
python -m pytest -q tests/property --hypothesis-show-statistics
```

[Hypothesis](https://hypothesis.readthedocs.io/en/latest/reference/api.html)의 `given`과
재현 가능한 설정을 사용합니다. 속성별 설정에 따라 최대 200~300개 사례를 생성하며 실패를 작은 입력으로
축소합니다. 실패 예시는 고정 회귀 사례로도 남깁니다. 테스트 전용 의존성이므로 일반 설치에는
추가되지 않습니다. 데이터셋 다운로드나 모델 호출은 없습니다.

검사는 원문/출력 좌표 보존, 이메일 문장 경계, Vault 왕복 및 토큰 충돌 방지,
겹침 알고리즘의 단순 참조 구현과의 일치, 필드 격리를 다룹니다. 실제 도메인 정확도,
새로운 모든 공격/문서 양식, 개인정보의 법적 익명성을 보장하는 벤치마크는 아닙니다.
